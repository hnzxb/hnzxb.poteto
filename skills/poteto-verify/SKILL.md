# Poteto Verify（验证技能）

核心思想来自 poteto：**验证 = 给 Agent 手和眼**。没有验证就没有真正的 loop——Agent 看不到自己工作的结果，人就成了瓶颈代理。与本机「变更验证铁律 / Review Proof, Not Code」融合为本技能。

## 首次进入项目（初始化）

1. 探测项目形态：
   - 有 `justfile` → 优先复用/新增 recipe（如 `just test`、`just check`、`just e2e`）。
   - 无 justfile 且为 bun 项目 → 在 `package.json` scripts 补充（如 `bun test`）。
   - Nuxt/KeepModules 项目 → 静态门禁 `just check`（ESLint）优先。
2. 生成功能地图 `docs/功能地图.md`（中文标题命名，遵守文档命名规范）：

   ```markdown
   # 功能地图

   | 功能 | 到达路径（路由/命令/入口） | 验证命令 | 证据形态 |
   |---|---|---|---|
   | 登录 | POST /api/login | bun test tests/login.test.ts | 退出码 0 + 响应样本 |
   ```

3. 功能地图是**物化记忆**：每个功能一行，验证命令必须可直接复制执行。

## 每次修改核心逻辑后（例行）

1. **静态门禁前置**：先过 lint/类型检查（`just check` 或等价），不过不进下一步。
2. 按功能地图找到对应验证命令，**实际执行**，记录：
   - 命令原文 + 退出码
   - 关键输出片段（HTTP 请求/响应样本、CLI 输出快照、UI 截图路径）
3. 证据不足时升级验证层级（对齐验证光谱，成本从低到高）：
   - 运行时验证：真实跑应用、像用户一样请求/操作（Hono 项目用 `bunx --bun @hono/cli request`）
   - 集成验证：真实数据库实例（PGlite / SQLite 内存）
   - 属性验证：核心状态机/计费/并发用 `fast-check` 属性测试
   - 形式验证：仅当测试触达不了破坏场景（竞态、重试、状态机）时才引入 TLA+，不做玩具级滥用
4. 输出一行结论：`✅ <命令> 退出码 0，<证据摘要>`；失败就如实报错并修，禁止宣称完成。

## 维护

- 新功能落地时同步在功能地图加一行；发现地图与实际漂移，先修地图再验证。
- 验证脚本只收敛到 justfile / package.json / tests，**不在会话里现写一次性脚本**（那正是 poteto 说的不确定性来源）。
- 废弃验证脚本走 `archive/{yyyy-mm-dd}/` 归档，不直接删除。

## 禁止

- 凑覆盖率的示例单元测试（对齐全局测试策略：契约 / 不变量 / 集成三层优先）。
- 用 mock 全家桶替代真实集成路径的核心用户流验证。
- 仅凭"代码逻辑看起来对"交付。
