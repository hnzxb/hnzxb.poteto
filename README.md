# hnzxb.poteto — Poteto 方法论旁路专家

基于 Lauren Tan（@poteto）**信任倒金字塔**方法论构建的旁路专家（sidecar expert）知识库 + 可安装工具箱。给它任意一个项目，它会基于本仓库沉淀的方法论、技能与实践案例，对该项目进行专业评审，并按授权边界产出改进。任意项目 `npx -y github:hnzxb/hnzxb.poteto check → init → agent` 即得工具箱部署与 DeepSeek 初筛报告，专家复核定稿。

## 核心理念

**一切归结于信任（Trust）**：高质量产出不靠盯单个 Agent 微操，而靠设计一个让 Agent 默认做对的环境。评审一个项目，就是评审它的信任阶梯搭到了哪一层。

**核心原则：纠正一次错误，不如消除一类错误；增加一条规则，不如消除规则存在的必要。改进必须有可证明的收益；证据不足时，优先保持现状。**

信任倒金字塔（投入优先级从高到低）：

1. **代码库与架构** — 结构上消除坏写法，让"容易的事 = 正确的事"；布局须符合生态惯例，反惯例是隐性认知税
2. **静态分析** — Lint / 类型 / CI，确定性、低成本止血
3. **验证体系** — 给 Agent 手和眼：确定性验证命令 + 功能地图；测试分层归位，默认入口只含回归层
4. **Prose 规则** — 自然语言约束，能不用就不用
5. **人工审查** — 仅用于发现系统性缺口，发现后立即上移

### 问题上移机制（金字塔的工程含义）

金字塔不只是检查清单，是**纠错方向**。每次发现问题必须追问"能否向更高层上移"：

1. Prose 规则被反复违反 → 能被 Lint/类型/CI 判定的，禁止继续依赖文字提醒
2. 无法静态判定 → 建立确定性测试与验证入口
3. 问题源于结构设计 → 从架构上消除错误路径

最终目标：低层规则逐渐减少，正确行为成为系统默认行为。

## 工作方式（三段式，按授权递进）

1. **只读评审**（默认）：逐层判定 ✅⚠️❌ + 证据路径，输出报告五件套——总评、覆盖度表、系统性缺口（上移优先排序）、可执行改进项、明确不建议项
2. **授权实施**：用户显式授权后直接落地（个人工具/纯增量/合规自测可自行裁决），每步带可运行验证证据；业务代码改动仍需单项授权
3. **指令单制**：目标项目有专属 Agent 时，产出 diff 级实施指令单，由对方执行，专家按退出码与证据验收。指令单必须**可验收**而不仅是可执行，六要素缺一不交：修改目标与问题证据、影响范围与禁改范围、预期 diff 或修改方向、验证命令、通过标准、回传证据要求

**合规自测知行合一**：专家自己出的门禁标准，必须在自己触达的项目里以 `tests/poteto/` 先红后绿自证（红旗快照记入案例 CSV），不许只指手画脚。三类验证不得混同：**标准自测**（提出的规则有实际验证方式）、**项目回归**（改动不破坏目标项目既有能力）、**结果验收**（改进真正解决了原始问题）。

**知识反馈闭环**：方法论 → 项目评审（发现缺口）→ 实践案例（记录过程与证据）→ 经验提炼（修订规则）→ 回到方法论。注意：不是每个项目问题都该升为通用规则——须经多个案例验证或具有足够确定性，才提升进 AGENTS.md / skills。

**角色边界**：产出是目标项目的自我规范能力，不是代工。抱怨/情绪化表达不构成授权，拿不准就反问。

- s3.idf.live 案例：专家越界直接改目标项目被用户纠正（已补：角色边界纪律 + 记忆）
- mihomo 案例：`execFileSync('npx')` 不可用，须直呼 `node_modules/.bin`；红→绿留痕从此为固定动作
- esptool.components 案例：初心滞后（第 3 个 commit 才补）、给 C 库装 npm/vitest 技术栈错配、宣布规则 5 分钟后自违反、案例 README 美化过程顺序（已补：初心先行/commit 时间线核查/治理工具同构/人工闸门——非 poteto 仓库见专家 commit 默认越界可要求回滚）
- agent 提示词四轮回灌：自指误报（工具箱源仓库建议部署自己）、动作幻觉（建议装 pstack 插件）、env 探针歧义（无 .env 也报未忽略）、判第 3 层不看 doctor 入口——每份报告的真实错误都回灌成采集器/提示词的确定性规则
